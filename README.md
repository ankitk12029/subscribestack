# SubscribeStack

A subscription-analytics semantic layer + AI-agent verification harness, built on synthetic data to explore the kind of work described in RevenueCat's Data Analyst job posting.

**No RevenueCat data — real or otherwise — is used anywhere in this project.** Every row of every dataset here is synthetically generated (`scripts/generate_data.py`, fixed random seed). The domain gotchas are modeled after the *shape* of problems the job posting itself describes, not any real company's actual data or definitions.

## Why this project exists

The job posting says the most valuable thing on the team isn't SQL, it's domain knowledge: knowing what a trial start actually counts, why tracked and realized revenue differ, how refunds land in the data. It also asks for comfort with AI agent tooling grounded in a semantic layer, and being "appropriately skeptical" of AI-generated answers — able to explain *how* an answer was verified, not just how it was produced.

Rather than just list those things on a resume, I built a small system that has to actually get them right:

1. **A synthetic subscription business** with the exact edge cases that make this domain hard — trials that get cancelled the same day they start, refunds that land weeks after the original charge, tracked vs. realized revenue.
2. **A dbt project** where those edge cases are resolved once, in documented models, instead of every downstream query having to remember them.
3. **An AI agent** that answers natural-language business questions using *only* that documented semantic layer — and, critically, cross-checks its own numeric answers against independently-written reference queries, flagging mismatches instead of returning a wrong number with false confidence.
4. **A dashboard** built on top of the same trusted marts.

See the commit history for how this was actually built, including a real bug (naive trial counting) that the agent's sanity-checking caught, and the fix that followed.

## Architecture

```
seeds/                  synthetic raw data (users, subscription events)
models/staging/         thin cleanup views over the raw seeds
models/intermediate/    where the domain logic actually lives (see below)
models/marts/           the only tables anyone (dashboard or agent) should query
agent/                  NL-to-SQL agent + independent verification harness
dashboard/               Streamlit app reading from the marts
```

### The three gotchas, and where they're resolved

| Gotcha | Resolved in | How |
|---|---|---|
| Same-day-cancel trials inflate trial-start counts by ~12% | `models/intermediate/int_trials.sql` | `is_countable_trial` flag; documented in `schema.yml`, enforced by a dbt test |
| Refunds land under their own date, not the original charge's date | `models/intermediate/int_revenue.sql` | Every refund/chargeback is netted back to the *original* transaction's `charge_date` |
| Tracked revenue ≠ realized revenue | `models/marts/fct_revenue_daily.sql` | Both columns exposed explicitly; the gap is documented as expected, not a bug |

### The verification harness (the part I'm most interested in talking about)

`agent/reference_checks.py` holds a small set of independently-written SQL queries — not generated by the LLM — for a few common question shapes (trial counts, conversion rate, realized revenue, all by month). Every agent answer that matches one of these shapes gets cross-checked against its reference value; anything off by more than 0.5% is flagged with an explanation of what likely went wrong, rather than silently returned.

Run `python3 agent/agent.py --demo` to see this catch a real mistake: one of the demo questions deliberately asks the agent to run a naive `COUNT(*)` against the raw events table (the exact bug fixed in commit 6), and the verifier flags the 12.5% deviation from the documented, filtered number.

## Running it yourself

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt

# 1. Generate the synthetic data
python3 scripts/generate_data.py

# 2. Build the dbt project (creates warehouse.duckdb, runs models + tests)
dbt build

# 3. Ask the agent questions
python3 agent/agent.py --demo                         # canned demo, no API key needed
OPENAI_API_KEY=sk-... python3 agent/agent.py "How many trials converted in June 2024?"

# 4. Launch the dashboard
streamlit run dashboard/app.py
```

`~/.dbt/profiles.yml` needs a `subscribestack` profile pointing dbt-duckdb at a local file — see the profile block in this repo's setup notes, or dbt-duckdb's own docs.
